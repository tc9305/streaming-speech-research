# SimulST 動態熱詞與記憶機制：研究現況、問題定位及下一步

**報告日期：2026 年 10 月 30 日**  
**性質：與指導教授討論用的研究進度報告（非完成實驗的成果報告）**  
**研究方向：Dynamic Hotword × Bilingual Term Pairing × Hotword Memory × Streaming Speech Translation**  
**已知前提：可以在指定時間點取得並加入熱詞；本階段不處理投影片偵測。**

> **一句話總結**：相關研究已經從「熱詞注入」進展到「術語檢索、證據式啟用與記憶工作集合管理」。我想先做出可重現的 Zipformer/Transducer 即時熱詞基準，接著比較「防止錯誤熱詞污染記憶」與「RVQ 大型術語庫」哪一條更適合成為我的主要研究貢獻。

---

## 第 1 部分｜目前想解決什麼問題（約 1 分鐘）

**給教授看的重點**

- 目標應用：中文技術演講 → 即時英文字幕；必須兼顧術語正確率、一般文字品質與延遲。
- 系統需求：已知時間點注入中文熱詞，保存 `source_term ↔ target_term`，並控制熱詞何時啟用、降權、停用或恢復。
- 本階段排除投影片辨識，以「指定時間點的熱詞更新事件」模擬外部資訊進入系統。
- 想確認的不是能不能做熱詞清單，而是**什麼情況下偏置有益、有害，以及記憶如何安全更新**。

**口頭講稿**

「教授，我這次把研究問題再縮小一些。原本的目標是把動態熱詞、雙語術語配對跟 Hotword Memory 整合到即時中英語音翻譯。因為現在已經假設我知道哪個時間點有新熱詞，所以我先不研究投影片偵測，而是直接模擬時間事件，把新的中文術語和指定英文翻譯加入系統。接下來我希望先驗證熱詞到底能幫助多少辨識與翻譯，以及錯誤或過期熱詞會不會造成干擾。」

## 第 2 部分｜已確認的文獻現況（約 2 分鐘）

| 研究 | 做了什麼 | 跟我原本構想的重疊 | 我可以研究的差異 |
|---|---|---|---|
| **RASST**（EMNLP 2026） | 部分語音的跨模態術語檢索，增量翻譯時判斷是否與何時使用術語 | SimulST、雙語術語、動態候選 | 非 Zipformer/RNN-T 專用，也沒有將 RVQ 作為 Hotword Memory |
| **EGTA**（2026 預印本） | 從文件建立術語記憶、以串流局部證據選擇候選，作用於 ASR/語音側及翻譯解碼側 | Memory、Evidence-based 啟用、ASR/MT 偏置 | 沒有以 RVQ、共享 Codeword 更新或長期記憶防污染為主要方法 |
| **AutoTerm-SST**（2026 預印本） | 在大型術語庫中依近期翻譯上下文選擇 Topic Slices，維持有限 Active Working Set | Memory Activation、主題切換、舊詞退出 | 以 Topic-level Routing 為主，非 RVQ Codebook |

**口頭講稿**

「我找到幾篇跟這條方向很接近的論文。RASST 已經在 SimulST 裡做部分語音的術語檢索，並研究什麼時候使用檢索結果。EGTA 已經把術語整理成 Memory，根據局部辨識證據選取候選，再用於 ASR 與翻譯端。AutoTerm-SST 也已經把大型術語庫分成 Topic Slices，隨著主題變動維持 Active Working Set。另外 Apple 的研究已用 FSQ 壓縮大量 ASR 的 Contextual Biasing Entries。所以我現在認為，如果只說我要做動態熱詞、Memory，或換成 RVQ，都不能直接當成主要創新；需要更明確地定義要改善的問題。」

**目前判斷（不要宣稱已證明）**：尚未在這次檢索中確認到一篇完全結合「SimulST × Dynamic Hotword × 雙語配對 × RVQ Hotword Memory」的論文；但這不等於此技術組合一定具有足夠的原創性。

## 第 3 部分｜我的三個技術判斷（約 1.5 分鐘）

### 3.1 已知時間點加入熱詞後，要怎麼做？

先使用已存在的 streaming Transducer，從以下路徑做實驗：

`熱詞更新事件(time, source, target) → Active Term IDs → 中文 Tokenization → Context Graph / Decoder-side Biasing → Streaming ASR → 增量 MT（使用雙語配對）`

在固定的解碼邊界／Chunk 切換有效熱詞；**不要先假設可以在相同 Stream 中無狀態重建 Context Graph**，必須測試實際 API 的狀態管理行為。

### 3.2 RNN-T Prediction Network 還是 Joiner？

- **第一版**：先不改 Prediction Network 或 Joiner 的參數；在 Joiner 產生的 token scores 後加 Contextual Beam Search Biasing，得到可控制的 Baseline。
- **需要改模型時**：比較 Prediction-side Context Adapter 與 Joiner-side Context Adapter。後者可在聲學 Encoder 和歷史文字表示的交會點融入候選術語；但優劣必須用實驗證明。
- **不要混淆**：在 Joiner 後的解碼分數加分，**不是**重新訓練 Joiner。

### 3.3 Hotword Memory 怎麼清理？

- Term Record：`term_id / 中文術語 / 英文譯文 / 來源 / 確認狀態 / 最近有效時間 / pinned / code_ids(可選)`。
- Active / Session / Long-term 三層；低相關詞先**停用或降權**，不等於永久刪除。
- Memory 不能只用被偏置後 ASR 的結果自動提高該熱詞信心，否則可能「偏置 → 誤辨識 → 回寫 → 更強偏置」。
- 若使用 RVQ，多個術語可能共用 Codewords；刪除一筆術語應移除其 `term_id` 與索引，**不應刪除共享 Codeword**。

**口頭講稿**

「在實作上，我目前想先保留預訓練的 RNN-T，做 Decoder-side 的熱詞加分，而不是一開始就改 Prediction Network 或 Joiner。這樣比較容易先確認熱詞注入是否有效。另外，Memory 我認為應該把『停用』跟『永久刪除』分開處理，尤其不能直接把被加分後的辨識結果當成記憶更新的可靠證據，否則系統可能持續強化錯誤。」

## 第 4 部分｜兩條候選研究路線（約 2 分鐘）

### 路線 A（我較推薦先做）：Verified Dynamic Hotword Memory

**核心問題**：錯誤、過期或發音相近的熱詞會不會造成錯誤累積？如何在不犧牲一般詞正確率的情況下更新或恢復 Memory？

**候選方法**：

1. 同步記錄有熱詞偏置與未偏置時的候選分數、Partial Hypotheses 及術語穩定性（不一定永久跑兩套完整解碼）。
2. 設計 Evidence Gate：Accept / Defer / Suppress，決定熱詞是否可影響解碼或被寫入 Session Memory。
3. 當熱詞造成衝突時，降低 Active 權重；新的獨立證據成立時才恢復。
4. 雙語配對以 Term ID 維持，不因一次錯誤轉寫就覆寫正式英文譯名。

**可能的新貢獻（待驗證）**：術語偏置結果與記憶更新之間的防污染機制，而非僅做 Bias 開關。必須與既有 Adaptive Contextual Biasing 比較。

### 路線 B（有明確大型術語庫需求才做）：RVQ-based Bilingual Hotword Memory

**核心問題**：在固定記憶體、檢索與更新延遲限制下，RVQ 是否比 FP32/FP16、PQ、FSQ 更適合管理大型、會持續加入或移除的雙語術語庫？

**候選方法**：`Term Encoder → RVQ Codes → 近似檢索 → Top-K Term IDs → 中文 Context Graph + 英文術語控制`。共享 Codebooks 離線訓練並固定；在線只更新 Term Records 與索引。

**最大風險**：若每次已知時間點只加入幾個確切詞，直接 Tokenize + Trie 就夠了；RVQ 會增加系統複雜度，卻可能沒有收益。

**口頭講稿**

「我目前考慮兩個方向。第一個是研究熱詞記憶的可靠性，尤其是錯誤熱詞加分之後，會不會造成後續記憶污染，以及怎麼利用獨立證據控制它的更新。第二個才是 RVQ Codebook，研究大規模術語庫在固定資源下的檢索和更新。但如果我們現在只在指定時間加入少量已知熱詞，RVQ 不一定必要，所以我想先讓實驗結果決定它有沒有價值。」

## 第 5 部分｜我打算先做的最小實驗（約 1 分鐘）

**Baseline**：同一個中文 Streaming ASR + 增量中英 MT，不改模型權重；確保合法的時序，只在指定時間點之後啟用熱詞。

| 實驗條件 | 目的 |
|---|---|
| E0：無熱詞 | 基準表現 |
| E1：固定熱詞清單 + 相同 Bias Strength | 熱詞有無基本增益 |
| E2：已知時間點更新熱詞、固定 Bias Strength | 檢查動態注入流程與狀態是否正確 |
| E3：加入錯誤／同音近音／過期熱詞 | 量化誤觸發、一般詞受害和記憶問題 |
| E4：Evidence Gate + 可逆 Memory 更新 | 驗證路線 A 的貢獻 |
| E5：FP32/FP16/PQ/FSQ/RVQ 檢索比較（條件式） | 先確認路線 B 是否值得投入 |

**重要指標**：中文 CER、Hotword Precision/Recall、False Hotword Trigger Rate、英譯術語正確率、一般句子翻譯品質、p50/p95 端到端延遲；若走 RVQ 另加 Recall@K、index update time、記憶體占用量。

**測試情境**：正確熱詞、熱詞不出現、相似發音干擾、指定時間新增／移除熱詞、同一詞不同英文譯名、連續語音與主題轉換。資料集須區分開發與測試，避免用測試語音調整 Gate 門檻。

**口頭講稿**

「在實驗上我想先不用重新訓練大模型，而是建立沒有熱詞、固定熱詞、動態熱詞及加入干擾詞四個基準。先把熱詞準確率、誤觸發與即時延遲量出來，再決定要做防污染 Gate 或 RVQ 壓縮。這樣比較容易知道研究問題是不是真的存在，也比較能做消融實驗。」

## 第 6 部分｜我希望教授幫我決定的四件事（約 1 分鐘）

1. **主要投稿貢獻應放哪一層？** 偏 ASR／RNN-T 的 Contextual Biasing，還是完整 SimulST 的雙語術語翻譯品質與延遲？
2. **是否同意先不動 Prediction/Joiner 的模型參數？** 先做可控的 Decoder-side Baseline，等觀察到實際缺陷再評估 Joiner Adapter。
3. **RVQ 是否必須是主線？** 如果目標術語規模只有數百筆，能否先以 Memory 可靠性為主；若研究目標是數萬至數十萬筆，才啟動 RVQ/FSQ 比較？
4. **第一階段的可驗收成果是什麼？** 建議兩週內交出「定時注入熱詞的 Streaming ASR Demo + 失敗案例 + 初步 CER/術語指標/延遲」，再一起定正式實驗。

**收尾講稿**

「所以我明天最想確認的是研究核心應該放在哪裡。我目前比較偏向先建立能運作的 Dynamic Hotword Baseline，再研究錯誤熱詞對記憶更新與串流辨識的影響。RVQ 我仍然有興趣，但我希望它是為了解決明確的大規模檢索或容量問題，而不是先決定技術再找問題。想請教授幫我判斷，哪個方向比較有研究貢獻，也比較適合我先做第一個實驗。」

## 可直接提出的 4 個觀點

1. **「注入時機已知」不等於「術語一定要被使用」**：時間事件只代表可用，不代表語音裡真的出現；所以還要有聲學／文字證據。
2. **Dynamic Memory 的關鍵可能不是容量，而是錯誤回饋**：偏置後的結果不能直接當作回寫依據，否則系統可能自己強化錯詞。
3. **RVQ 應該是被實驗需求推導出來的**：先證明 FP32、FP16 或 FSQ 在規模／延遲上不足，再談 RVQ 的價值。
4. **真正的 SimulST 評估要包含連續語音**：短句 CER 或 BLEU 不夠，需要量字幕延遲、主題切換與穩定性。

## 若教授追問，建議這樣回答

**Q：你所謂的 Novelty 在哪？**  
A：「我目前還沒有把它視為已成立的 Novelty。我想先驗證現有方法未充分處理的『偏置結果回寫造成記憶污染』，比較基準包含固定 Biasing、Adaptive Biasing、規則式 TTL 與證據式 Gate；如果沒有明確改善，就不把它當主要貢獻。」

**Q：為什麼一定要用 RNN-T Joiner？**  
A：「不一定。先用 Joiner 輸出之後的解碼偏置建立 Baseline，因為不需要動模型權重。如果後續發現只有分數加權無法區分相似發音術語，再評估在 Joiner 附近加小型 Context Adapter。」

**Q：如果你知道什麼時間加入什麼熱詞，為什麼還要 RVQ？**  
A：「少量確切詞其實不需要。因此我不會預設 RVQ 是主線，只有在大規模術語庫、跨主題檢索和固定資源預算的設定下，RVQ 才值得與 FSQ/PQ 比較。」

**Q：會不會只是把現成方法接起來？**  
A：「所以我先把組件整合當 Baseline，不當論文貢獻；真正研究的部分要提出可檢驗的 Gate/Memory 更新規則或量化檢索方法，並且用消融實驗證明它改善了哪一個指標。」

**Q：你現在做出結果了嗎？**  
A：「目前是文獻梳理與方法設計階段，還沒有可報告的模型實驗結果。下一步是建立固定與動態熱詞的 Baseline，讓研究問題有實際量測依據。」
